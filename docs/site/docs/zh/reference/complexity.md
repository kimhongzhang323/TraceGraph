# 图执行复杂度参考

本页讨论影响 TraceGraph 执行复杂度（时间、并发、资源）的主要因素，并提供估算与缓解建议，帮助在设计阶段做出权衡。

主要影响因素

- 节点数（N）：图中节点的总数，线性影响节点遍历次数（最佳情况）。
- 并行分支因子（B）：`parallel(...)` 或 `sendAll(...)` 导致的并发分支数。总工作量近似乘以分支因子；并发执行会增加瞬时资源需求（线程/虚拟线程、内存）。
- 外部 I/O 时间（T_io）：每个节点执行的外部调用时延（HTTP/DB/LLM）。这是常常主导执行时间的因素。
- 重试与回退（R）：重试策略会将失败节点的成本放大。指数退避 + 最大尝试次数会显著增加最坏情形成本。
- 回放（replay）与 Trace 大小（L）：保存/回放步骤会在磁盘/数据库层产生额外开销，Trace 大小影响存储与网络传输成本。

复杂度估算（粗略）

单次执行的近似总耗时（串行）:

T_total ≈ Σ_i (T_cpu_i + T_io_i * (1 + expected_retries_i))

并行分支的资源峰值近似：

PeakWorkers ≈ baseWorkers + max_over_parallel_nodes(Σ branches)

注意：上式为粗略估算，真实行为取决于节点是否会阻塞线程或友好地在虚拟线程上阻塞。

设计与优化建议

- 把阻塞 I/O 保持在虚拟线程友好的实现（JDK 21 虚拟线程）或采用异步节点以减少线程占用。
- 尽量把昂贵的外部调用合并或缓存（`MemoryStore` / 本地缓存）以减少重复请求。
- 对高分支并行使用批处理或限制并发（令牌桶 / 并发限制器）。
- 对高失败率节点降低默认重试次数并把重试策略声明为图级可配置项。
- 在设计时给节点设定资源预算（预估 T_io）并在 `NodeListener` 中记录真实耗时，用于后续调优。

测量与可观测性

- 在 `NodeListener.onEnter`/`onExit` 中记录时间戳与 token 使用，帮助计算真实延迟分布。
- 对关键路径（hot path）添加采样级别的详细 trace，以便在生产环境中不导致过度开销。

示例

如果一个图包含 10 个节点，每个节点平均外部调用延迟为 200ms，且预期无重试，则粗略总耗时 ~ 2s。若在某节点使用 parallel(5) 并且每个分支又触发 200ms 的外部调用，则峰值并发外部调用为 5 个，瞬时延迟不变但需要更大并发容量。

练习：针对一个有 3 个并行分支的子图，测量在 100ms、200ms、500ms 三种外部调用延迟下的平均执行时间，并使用 `NodeListener` 汇总结果。
